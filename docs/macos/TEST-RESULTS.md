## Методика и пределы

Время воркеров без минутного ожидания: 100 — 2,068 с; 250 — 4,959 с;
500 — 10,261 с. Пределы квоты/интервала/соединений и защита повторов включены.
Это не скорость внешней доставки и не время штатного календарного расписания:
20 отправок/такт требуют минимум 5/13/25 минутных тактов.
RAM/CPU относятся к Python-процессу приложения вместе с локальными почтовыми
фикстурами. PostgreSQL находится в другом контейнере на постоянном томе.
Задержки, timeout, разрыв после DATA, 451, auth error и API ограничения проверены
отдельными регрессиями. Настоящие Gmail/Microsoft/Яндекс/Mail.ru не использовались.

Первый PostgreSQL-прогон на tmpfs прервался из-за заполнения временного диска:
305 passed, 7 failed, 305 errors. Его результаты не засчитывались как успешные;
после переноса стенда полный набор повторён. Промежуточный SQLite-прогон имел
2 failed из-за конкурирующей записи в SQLite; эти транспортные тесты для SQLite
сериализованы, конкурентность подтверждена на PostgreSQL. Подробности в аудите.

## Воспроизведение

Обычный набор:

```bash
.venv/bin/python -m pytest -q
TEST_DATABASE_URL='postgresql+asyncpg://USER:PASSWORD@HOST/EMPTY_TEST_DB' .venv/bin/python -m pytest -q
node --test frontend/scripts/localize.test.cjs
```

PostgreSQL-набор пересоздаёт таблицы: указывайте **только отдельную тестовую БД**.
Недоступный явно заданный PostgreSQL вызывает ошибку, а не переход на SQLite.

Специальные стенды: `tests/support/seed_restore.py`, `restore_postgres.py`,
`migration_copy.py`, `load_mail.py`, `mcp_wire.py`. В них проверяются имена/адреса
изолированной среды `quickly_r2_*` / `quickly-revision2-*`. Запускайте их через
`PYTHONPATH=.`; для restore нужны Linux pg_dump/pg_restore в тестовом контейнере.
Сценарии работают с синтетическими данными, сохраняют прежние базы/копии и не
используют рабочий `quickly-mac` или внешний почтовый транспорт.

Результаты JSON: [нагрузка 100](reports/load-100.json), [250](reports/load-250.json),

## Установленная программа

Установленная программа отвечает на **http://localhost:8765**, HTTP 200;
вход существующего администратора проверен (200), страница диагностики открыта.
Оболочка `~/Applications/Quickly.app` проходит codesign-проверку. LaunchAgent
`local.quickly.start` фактически запущен и завершился с кодом **0**; его файлы
находятся вне Documents. Plist корректен. Физическая перезагрузка Mac не выполнялась.

Перед обновлением и последним обновлением image созданы новые dump; каждый
восстановлен в отдельную проверочную базу. Старые dump, ключи и image сохранены.
После основного обновления сравнены все прежние бизнес-значения **49 таблиц**;
перед/после окончательной сборки — **50 таблиц**, включая новую таблицу запрета чтения.
Сохранены **1 администратор и 1 SMTP-аккаунт**; контактов, кампаний и почтовых
операций — 0. Отправка реальных сообщений не выполнялась.
**STOP=true, campaigns_enabled=false, включённых диагностических планов 0**.
Общий предел почтовых соединений — 4. Quickly доступен только с этого Mac;
порт PostgreSQL наружу не опубликован. Рабочий PostgreSQL не перезапускался.
[Машиночитаемый результат](reports/deployment.json).

Из сравнения исключены только дата обновления настроек и служебный маркер
`global_recalc_finished_at`. Все прежние уведомления сохранены; дополнительные
уведомления об ошибке подключения сохранённого SMTP-аккаунта допустимы и не
скрывались. Тип уведомления в коде называется `token_expired`, но он сам по себе
не доказывает истечение OAuth: сохранённый аккаунт использует SMTP. Успешное
соединение с ним и внешняя доставка пока не подтверждены.

Первый контроль обновления ошибочно счёл служебный маркер и новые уведомления
изменением данных. Попытка служебного отката `pg_restore --clean` столкнулась с
новой FK-связью и завершилась ошибкой; вся SQL-транзакция была отменена, частичного
восстановления не было. Программа была временно остановлена. Сопоставление с
проверенной копией подтвердило сохранность прежних записей, после чего новая
версия запущена. Этот обходной способ больше не использовался: штатное
восстановление теперь переключает подготовленные базы и сохраняет прежнюю.
Последнее обновление затронуло только очистку ошибок/CSV, без изменения схемы;
контроль сохранности прошёл.
